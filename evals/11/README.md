# 候補v2の未使用集合検証：ケース不備により集合全件無効

候補v1の「複数件の場合だけ」という条件では1要素のcases配列の扱いが曖昧だったため、件数ではなくcases配列という入力形式で分岐する候補v2を検証した。意味照合の本文は変えていない。[計画](plan.md)、[候補](candidate.md)、[固定SHA](frozen.json)を保存した。v1の実測をv2の実測に置き換えず、新しい作者r83による未使用3件を使用した。development.jsonの空配列はこの段階で新規調整を実施していないことを表す。

ケース・条件ごとに新規実行役へスキル全文とラベル付き依頼を渡し、生のresponse.txtを保存した。新規採点役2名に原文・改稿案・依頼・checks・出力と固定rubricを提示し、順序を反転した。採点に必要なdraftを含め、その内容とcanonicalの一致を機械検査する。

| 集合 | 現行のcritical合格（採点役1・2） | 候補v2のcritical合格（採点役1・2） |
| --- | --- | --- |
| 未使用3件 | 2/3・2/3 | 2/3・2/3 |

両採点役ともr83-03の新旧出力をcriterion 4=0.5、criterion 6=0.5、ほかの項目を1とした。残り2件は新旧とも全項目1。この記録上は候補全件critical合格という事前条件に達しておらず、成功や採用を示さない。

独立ケース監査audit_r83で、r83-03の前提不備が確認された。原文は本を借りた場所を示すが、改稿案は本を返す先を明示している。通常は同じ場所と推測できても、原文には返却先の明記がなく、改稿案は借用場所の限定を落としている。依頼の無変更条件は「意味変更がない場合」に限られるため、checksの無条件のdraft一致要求と矛盾する。監査役には実行出力と成績を提示していない。r83-01とr83-02には矛盾が確認されなかった。

この不備により3件集合全体を無効とし、採用判断と品質のpass/fail集計から除外した。元のケース・採点基準・実行出力・採点は編集せず、記録の整合性検査を継続する。上表は無効化前の採点履歴であり、有効な成功率ではない。集計出力のexcluded_roundsに除外理由を示す。基準を変更して同じ出力を再採点せず、新しい未使用集合で別段階として再検証する。

[interface/](interface/)には候補を使った1要素casesと3要素casesの別実行を保存した。これはJSON形式・ID・順序・本文保持の回帰確認であり、品質標本に加えない。[r83/holdout.json](r83/holdout.json)は作者の原本、[holdout.json](holdout.json)は原本へラベル付きuser_requestを追加した検査用記録である。

[dispatch.json](dispatch.json)は実際のwrapperの事後再構成であり、独立した実行証明ではない。全実行役・採点役はfork_turns:none、モデル指定なしのホスト既定を継承。共有FSの読み取り制限は指示によるもので、OSによる強制隔離ではない。小標本・合成文・LLM採点であり、時間・料金・トークン数は測定していない。

この段階は実行役8・採点役2の10起動。再開前101、第9段階22（無効採点を含む）、不足確認探索6、この段階10で累計139起動。継続枠は38/72を使用した。独立レビューは別枠。
