# PR1：短い独自スキルの比較

## 問題と仮説

ルールを増やす前に、意味保持・必要箇所だけの編集・出力前照合で短文の推敲が成立するか確認する。実行用スクリプトや分野別分岐は、効果の根拠がまだないため採用しない。

- 原本: `60bf877acebc86651e0b67d70112a66245f87758`、SKILL blob `c9548eeb11754055a1f4b25136b7383ea8363bb3`
- 独自候補: [candidate.md](candidate.md)、Git blob `849f5b4b038522626734145d9373bf5f1219267e`

- 方法の参照SHA・ライセンス: [SOURCES.md](../../SOURCES.md)。

critical全項目を充足した件数。採点者ごとの判定を統合して隠さない。

| 条件 | 調整用・採点1 | 調整用・採点2 | 未使用・採点1 | 未使用・採点2 |

| 最小 | 5/6 | 4/6 | 6/6 | 6/6 |

読みやすさは全条件・全件で両採点者が1。原本と最小のD6は本文を保持したが、確認質問が「編集者に」を確認相手とみなしていた。独自は確認相手・伝達相手を区別して質問した。最小のD2の否定表現の言い換えは採点者間で評価が割れたため、確定した差として扱わない。

独自候補に、この集合で検出された回帰はない。未使用集合では条件間の差もない。単一試行・同じホストの合成短文であり、安定した成功率や一般的優位を示すものではない。

## 採否と次の課題

独自候補を採用。最小より少し長いが、調整用の曖昧な文を扱え、未使用集合でも悪化を検出しなかった。原本のルール・参照ファイル・スクリプト一式を製品に移す根拠は得られなかった。

一方、部分編集、引用の保持、用語指定、厳密な構造化出力、長文は未検証。次は本文中の引用・編集対象外の扱いを調べる。今回の読みやすさ得点が飽和していることもあり、短文6件だけで改善の完了を判断しない。

## 記録と再実行

[development.json](development.json) と [holdout.json](holdout.json) が入力とケース別チェック。[metadata.json](metadata.json) が匿名IDと条件・担当者の対応、[manifest.json](manifest.json) が記録のSHA256。

各実行ディレクトリのrequest.jsonとresponse.jsonに実際の入力・出力・自己報告を保存。採点用ディレクトリ6be/29eとe11/a52には匿名の入力・出力と固定基準、採点を保存した。2人目には候補の順を逆にした。自己報告は採点者へ渡していない。

再実行はrequest.jsonのskillとcasesを新規の会話非継承エージェントに渡す。原本ではskill_pathの代わりにreference-files.jsonのファイルを固定コミットから取得し、ライセンスとともに別の空ディレクトリに置く。出力を匿名化し、新規採点者へ採点パケットを渡す。既存のresponse.json・metadata.json・他条件は実行役と採点役に見せない。出力は確率的であり、再実行で一致する保証はない。

全担当はfork:none。共有ファイルシステムの読み取りを指示で制限したもので、OSレベルの隔離ではない。ホストのモデル名・tool_uses・duration_msは記録に直接提供されていないため未測定。自己申告のretriesとは区別する。原手法の時間・手数を含む収束判定は未検証。

`python3 tools/check_records.py` はJSONの可読性と保存記録のハッシュを検査するだけで、推敲の品質は採点しない。
