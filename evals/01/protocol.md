# 構造分析型スキルの初回評価

## 固定対象

- 参照元: `nanaism/yomiyasu` v2.0.1, commit `84e1f5b15e497538fcfe19ab7e9c6f6d138f19ff`（2026-10-17）。完全なコミットSHAは `SOURCES.md` に記録する。
- 候補: 本PRで新規作成する `skills/yomiyasu/SKILL.md`。
- 評価ケースとrequirements: [`scenarios.json`](scenarios.json)。候補スキルを書く前に固定し、候補に合わせて変更しない。
- requirementsは評価者だけに渡す。実行役には依頼、原文、対象スキルだけを渡す。

## 目的と判定

この比較は、項目を順番に当てるのではなく、日本語の文・節・段落が作る関係を読み手の目的に照らして捉え、その関係上の摩擦を解く編集ができるかを見る。構造分析をしたという自己申告ではなく、出力で保たれた関係、直された関係、または直さなかった理由を採点する。

各ケースの固定requirementsを ○ / × / partial で判定する。criticalがすべて○のときだけそのケースを成功とする。Accuracyは ○=1、partial=0.5、×=0 を合計し、requirements数で割る。読みやすさと編集範囲は、critical判定へ埋め込まず独立して採点する。基準の追加・削除・critical指定の変更は結果を見た後に行わない。

## 実行

1. 新規の実行役が参照元スキルと候補スキルをそれぞれ実行する。各条件1名・1バッチで3ケースを処理し、同一バッチ内のケースは独立でないと記録する。
2. 実行役には対象スキル、ケースID、依頼、原文だけを渡す。requirementsや採点基準は渡さない。両条件とも本文のみを返す指定のないケースは、各スキル自身の既定出力契約に従う。
3. 各実行役は成果物に加え、理解・計画・実行・整形のどこで迷ったか、指示から裁量で補った点、同じ判断のやり直し回数を報告する。これらは得点に混ぜない。
4. 新規の採点役2名が原文・依頼・匿名化したA/B出力・固定requirementsだけを見て独立採点する。一方は参照元→候補、もう一方は候補→参照元の順で見る。設計意図、候補名、実行役の自己申告は渡さない。二者が分かれた改善は改善として主張しない。
5. 指標はcritical成功、Accuracy、読みやすさ、編集範囲、未解決点、裁量で補った判断、再試行数。tool_usesとduration_msは呼び出し元から得られる場合だけ記録し、得られなければN/Aとする。

## 反復と停止

まず初回比較を行い、新たな不明点があればIssue / Cause / General Fix Ruleで記録する。候補修正は関連する一つの設計テーマに限り、requirementsとケースは固定する。各再評価には新規の実行役・採点役を使う。holdoutを見て修正した場合、そのケースは次回から調整用とし、新しい未使用ケースを先に固定する。

同じ種類の不明点が3ラウンド続けば、局所ルールを足すのを止め、構成を見直す。収束は、2回連続で新しい不明点がなく、critical失敗・品質回帰がなく、改善が小さい場合とする。1回の高得点だけで品質を一般化しない。固定された初回holdoutは一度見た後は未使用データとして扱わない。

## 解釈上の制約

3ケースの合成文と1つのモデル設定での小標本評価であり、一般的優位、利用者満足度、実運用での再現率、所要時間・費用の改善を主張しない。結果が同等なら、構造分析が過剰な手数や説明を増やさないかを見て採否を決める。
